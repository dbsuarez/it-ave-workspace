# Drawings (Excalidraw) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Excalidraw built into the app beside Canvas: channel/topic drawings and standalone drawings, live co-editing over Socket.IO, and offline drawing that merges back on reconnect.

**Architecture:** Excalidraw (React) is bundled with esbuild into one committed script, as the text editor already is. Drawings are rows holding the full scene (shapes including deleted ones). A live room per drawing relays changed shapes; the server merges them with Excalidraw's per-shape version rule and saves every 5 seconds. Access reuses channel and forum access. The client keeps a local copy in IndexedDB and merges on reconnect with Excalidraw's `reconcileElements`.

**Tech Stack:** Node, Express, Socket.IO, PostgreSQL, `node:test`, `@excalidraw/excalidraw` 0.18.1 + `react`/`react-dom` (dev dependencies, bundled), esbuild, IndexedDB, Electron 28.

**Spec:** `docs/superpowers/specs/2026-11-18-drawings-design.md` (approved 2026-11-18). Read it first; this plan argues from it.

## Global Constraints

- Limits (values from the spec): image 2 MB; drawing files 20 MB total; scene JSON 10 MB; 20,000 shapes; title 1 to 120 characters; server save every 5 seconds while changed, when the last person leaves, and on shutdown.
- **Zero third-party requests at runtime** (no fonts CDN, no library, no telemetry, no excalidraw.com). The app works with no network.
- A drawing with no `channel_id` is standalone. `topic_id` is allowed only for a topic of that forum channel.
- Access (every request and every socket event re-checks it): channel/topic drawing = anyone who can open the channel or forum (editor), guests view only; standalone = owner and invited editors edit, invited viewers view. View-only when the channel is archived or the topic is locked or archived.
- Shape conflict rule: higher `version` wins; on a tie the lower `versionNonce` wins; deleted shapes are kept (`isDeleted: true`).
- A drawing posted into a conversation is a message with `kind = 'drawing'` (and `topic_id` in a forum). Deleting the drawing turns the card text into "Drawing removed".
- All tables are created in `backend/src/migrations.js`. Run the backend with real-DB tests through `backend/test/helpers/scratchDb.js`. Names declared at the top level of client scripts must be unique across `frontend/src/*.js` (the build check enforces it).
- Never print `.env` values. Use the Write tool for files with quotes or backslashes. Push only when the user says so.

## Review Focus

1. A person outside the channel, department or share, a guest, and a viewer cannot read or change a drawing by any route or socket event: list, get, files, join, update, pointer (Tasks 3, 4, 5).
2. Edits made offline are not lost when reconnecting, including deletions and edits to different shapes of the same drawing (Tasks 2, 7).
3. Someone who loses access while a drawing is open is dropped within one save tick and their later updates are refused (Task 5).
4. A server restart loses at most the last save interval, and the client's local copy re-syncs the difference (Tasks 5, 7).
5. The app makes no request to any third party and the editor opens with the network cut (Tasks 1, 8).

### Task 5: Live editing hub (Socket.IO)

**Files:**
- Create: `backend/src/sockets/drawings.js`, `backend/test/drawing-live.test.js`
- Modify: `backend/server.js` (create the hub once, register each connection, flush on shutdown)

**Interfaces:**
- Consumes: Tasks 2 and 3; `socket.data.userId` (set by `sockets/chat.js` on authenticate).
- Produces: `createDrawingHub({ io, query, pool, saveEveryMs = 5000, now = Date.now }) -> { register(socket), flushAll(), tick(), shutdown() }`. Client events (all acknowledged with an object `{ ok, error? }`): `drawing:join { drawingId }` -> ack `{ ok, scene, files, revision, role, present }`; `drawing:update { drawingId, elements }`; `drawing:pointer { drawingId, pointer }`; `drawing:leave { drawingId }`. Server events to others in room `drawing_<id>`: `drawing:update { drawingId, elements, from }`, `drawing:pointer { drawingId, pointer, userId, username, color }`, `drawing:presence { drawingId, present }`, `drawing:revoked { drawingId }` to a person who lost access.

- [ ] **Step 1: Write the failing tests** (real DB, fake sockets as in `forum-posts.test.js`, a controllable clock and manual `tick()`): join returns the saved scene and role; a viewer and an outsider cannot join or update (ack error, nothing changes in the DB); an editor's update reaches the others and is merged (a lower-version update does not overwrite); the draw order of two editors' updates never changes the final scene; **save:** nothing is written before a tick, a tick after changes writes once and bumps `revision`, a tick with no changes writes nothing, the last person leaving flushes at once, `shutdown()` flushes; **revocation:** after an editor is moved out of the department (or banned, or removed from the share) the next `tick()` sends `drawing:revoked`, removes them from the room, and their later `drawing:update` is refused; updates that are malformed or oversize are refused without touching the drawing; presence lists the right people when they join and leave, and a disconnect leaves the room; two drawings do not leak updates into each other.

- [ ] **Step 3: Implement** the hub: an in-memory map of loaded drawings (scene, revision, dirty flag, members), the interval that calls `tick()`, the access re-check inside `tick()`, a pointer throttle (drop pointers faster than every 30 ms per person), and `server.js` wiring that also calls `shutdown()` on `SIGTERM`.
- [ ] **Step 4: Run** the new test, `test/socket-identity.test.js` and `test/forum-posts.test.js`; Expected: PASS.
